一、产品定位

这套系统面向大学物理课程，给一个班的学生和一位任课老师用。它要处理的事情很具体：学生做完诊断之后，知道自己该练哪几章；老师打开页面，能看出这个班这周谁掉队了。

市面上不缺通用 AI 助手，缺的是把校名、班级、课程章节、评价标准都长在系统里的东西。所以这里做成一个工作台：学生端八个视图，教师端五个视图，两侧共用同一套账号和数据。

1.1 它解决的问题

问题系统的做法
学情靠印象 八道前测题生成七维知识画像，每个维度给出掌握度；诊断结果直接决定项目匹配的排序
练习与课堂脱节 任务闯关按章节拆成关卡，每关提交后给对错和解析，记录写进学习报告
AI 只给结论、不给依据 AI 助教的回答带引用来源；评价复核里 AI 只出建议分，教师复核分与理由始终覆盖它
演示依赖网络和额度 工作台、六个预置课堂包、学习报告在断网时仍能完整使用；只有 AI 生成课堂需要联网

1.2 边界

有几件事系统不做，说清楚比含糊过去好：

  • 不做题库平台。题目跟着章节走，不提供跨课程的通用刷题。
  • 不替代教务系统。成绩、选课、学籍不在范围内。
  • 不做多租户。一套部署服务一个学院，校名字面量由构建期检查守住。

三、核心链路：一句话生成课堂

首页的输入框接受一句自然语言需求，比如「大学物理 第三章 牛顿运动定律」。提交之后系统做四件事：生成大纲、定角色、逐场景写内容、写讲稿与动作。四步之间是串行的，只有逐场景内容这一步内部并行。

图 2　一次生成请求的完整时序：大纲流式返回，角色与内容随后，最后落盘

3.1 为什么拆成四步

大纲先流式返回，学生能在十几秒内看到课程骨架，而不是盯着一个转圈。角色决定讲稿的口吻，必须在大纲之后、内容之前确定。讲稿和动作单独生成，是为了某一场景的配音出问题时可以只重做那一场，不必整堂课重来。

3.2 实测数据

阶段接口实测
课堂大纲/api/generate/scene-outlines-stream200，78.5 秒，15 个场景，收到 done 事件
智能体角色/api/generate/agent-profiles200，约 29 秒
逐场景内容/api/generate/scene-content200，单场景 60–82 秒
讲稿与动作/api/generate/scene-actions200，约 10 秒

内容生成是整条链路的耗时大头。四路并发之后，四个场景的总墙钟从 317 秒降到 83 秒，单请求没有被拖慢，说明瓶颈在模型输出长度而不是排队。

一个必须说清楚的地方：一次完整的十五场景课堂，端到端大约八分钟。演示视频里那段生成是真实录制的，中间按 52 倍速快进，角标写明了真实耗时。

3.3 失败怎么处理

大纲流在中途断开时，已经解析出来的场景会被保留并直接收尾，不整批重来。早期版本在这里做全量重试，两次生成叠起来必然撞上函数超时，最后连可用的十二个场景都拿不到。

模型返回的 JSON 不合法时，先走修复，修不好再重试，重试仍失败才把错误抛给前端。逐场景内容失败只影响那一场，其余场景照常生成。

四、技术架构

图 3　系统架构：浏览器本地优先，边缘函数只承担需要模型与网络的请求

4.1 前端

Next.js 16 的 App Router，React 19，样式用 Tailwind CSS 4。十三个视图走同一个动态路由，构建期静态化，因此首帧就有内容，不依赖客户端水合。

学生端和教师端共用一套外壳组件，导航项按角色过滤。角色门禁在布局层做：路径前缀决定角色，跨角色访问会被送回自己角色的首页，未知视图同样处理。

4.2 边缘

站点部署在腾讯云 EdgeOne Pages，加速区域选的是「全球可用区（不含中国大陆）」，函数落在新加坡。选这一档的原因是不需要 ICP 备案，代价是国内访问会绕一圈。

项目数值
函数最大执行时长120 秒（平台默认 30 秒，配置项 cloudFunctions.maxDuration）
函数包体积119.8 MiB（平台上限 128 MiB）
运行期路由65 条
Node 版本24.5.0

函数包体积是这条链路上最紧的约束。未裁剪的产物约 180 MiB，平台直接拒收。构建之后要跑一遍裁剪，把只用于构建的依赖、类型文件、source map 去掉，再上传。裁剪发生在「打包完成、上传之前」，所以不能用控制台的 Git 导入，只能走脚本或 CI。

4.3 模型

模型全部走 EdgeOne 的 Makers 网关，只接一个模型：minimax/minimax-m3。选它的理由只有一个：稳定。deepseek 那一路同一份大纲的逐场景内容，一次 30 秒成功、下一次直接 500，线上问题几乎无法复现。

MiniMax 有一个必须处理的特性：默认把思考过程写进正文，形如 <think>…，大纲的 JSON 解析会直接失败。实测只有 thinking: { type: "disabled" } 能真正关掉，reasoning_effort: none 和 chat_template_kwargs 都无效。这件事写在 lib/ai/providers.ts 里，改模型的人会看到。

4.4 存储

账号、学习证据、生成结果都在 localStorage，按账号 id 分区。换账号看不到别人的数据。服务端不存业务数据，只做模型代理和页面渲染。

账号表被写坏过一次，教训是：解析失败时不能返回空数组。现在的做法是先把原始内容备份到 physics-ai-accounts:corrupt-<时间戳>，再抛错让界面提示，绝不写回。

五、数据与安全

5.1 账号

用户名三到三十二个字符，允许字母、数字、下划线、连字符和中文。密码至少八位，用 PBKDF2 迭代 21 万次加十六字节随机盐存储，只存哈希。

student 和 teacher 是演示账号，注册时会被拒绝，避免同名账号和演示身份落到两套数据分区里。演示账号的登录路径不经过注册，密码是明文比对的，这一点在代码注释里写明了。

5.2 会话

登录后客户端写一个 physics_session Cookie，形如 <账号 id>.<时间戳>；同时所有发往本站 /api/ 的请求会带上 x-physics-session 请求头。门禁认其中任意一个。

这套会话只验形状，不验签名。它挡得住随手写脚本匿名调用，挡不住刻意伪造。真正的账号校验发生在本地，服务端没有账号数据库。这一点在参赛材料和代码里都是这么写的，没有含糊。

5.3 门禁范围

只守会消耗模型额度或上游资源的接口：/api/generate/*、/api/chat、/api/agent/*、/api/pbl/v2/evaluate、/api/transcription、/api/web-search。本地解析、材料上传、静态查询不拦，否则「断网也能演示」这句话就不成立。

5.4 凭据

模型 Key 只放平台环境变量，不进仓库。构建时有一道产物泄露门禁：扫描函数包，发现白名单外的环境变量名或凭据取值就中止部署。这道门禁拦下过一次真实事故——edgeone makers env set 会把变量同时写进本地 .env，下一次构建就把 Key 内联进了函数。

六、部署与交付

6.1 环境变量

变量用途
MAKERS_MODELS_KEYMakers 网关鉴权，控制台签发
MAKERS_MODELS模型白名单，本项目为 minimax/minimax-m3
DEFAULT_MODELopenai:minimax/minimax-m3
PARALLEL_SCENE_CONCURRENCY可选。未设置时，有 Makers Key 的部署默认四路并行

6.2 部署命令

本地部署跑 node scripts/deploy-edgeone.mjs，它按顺序做五件事：构建、裁剪、体积与泄露门禁、区域核对、上传。任何一步失败都会中止，不会带着问题上线。

持续交付走 GitHub Actions。推送到 feature/physics-ai-classroom 之后，runner 上跑同一条流水线。之所以不用控制台的「导入 Git 仓库」，是因为平台侧构建没有构建后钩子，裁剪插不进去，产物会卡在 128 MiB 上限。

6.3 两个容易踩的坑

第一，平台环境变量是构建期注入的。用 CLI 改完变量不重新部署，运行时读到的还是旧值。这一点实测过：env set 报成功，接口仍返回 0。

第二，Node 默认 IPv6 优先。在 IPv6 路由不通的网络里，fetch 会等到连接超时，报 fetch failed，而同一个地址用 curl 秒回。部署脚本里显式设了 IPv4 优先，CLI 子进程也一并传下去，否则它会把「查不到项目」当成「项目不存在」，接着去建项目，报一个跟网络毫无关系的「项目重名」。

七、性能与限制

7.1 实测

项目结果
静态页与动态路由线上自检 25 项全部通过
首帧十三个视图均为服务端渲染，首帧含校名与水合标记
单场景内容60–82 秒（本地直连网关）
四场景并行83 秒（串行 317 秒）
整堂课（15 场景）约 8 分钟

7.2 已知限制

生成速度。受模型输出长度限制，单场景内容很难压到 30 秒以内。换更快的模型能提速，但目前只有 deepseek 那一路明显更快，稳定性不过关，所以没换。

配额。Makers 配额是瞬时的，压测期间出现过 402，几分钟后同一个 Key 又恢复。四路并发会更快撞到窗口上限，现场演示前应确认额度。

函数包余量。119.8 MiB 对 128 MiB，只剩 8 MiB。新增依赖前要先看裁剪后的体积。

会话强度。如 5.2 所述，会话令牌没有签名，服务端只验形状。

7.3 验证方式

线上自检脚本覆盖 25 项：十五条关键路由、客户端 chunk、构建号、会话门禁三态、材料自引数字、模型供给。单元测试 164 例，集中在物理域、账号与会话、部署门禁三块。另有五个构建期门禁：校名字面量、上游品牌字面量、物理域依赖分层、i18n 键对齐、文档数字一致性。

这些检查都在 package.json 和 scripts/ 里，跑一条命令就能复现，不依赖某台机器的状态。
