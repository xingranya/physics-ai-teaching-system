## P0

### P0-1　会话门禁可被任意伪造，高耗能接口对全网开放

**证据（线上实测）**

```bash
# 不带任何凭证
$ curl -X POST https://dun.xran.uk/api/chat -d '{}'
401 {"errorCode":"INVALID_REQUEST","error":"Login required"}

# 带一个自己编的令牌（完全不需要登录）
$ curl -X POST https://dun.xran.uk/api/chat \
    -H 'x-physics-session: attacker.1700000000' -d '{}'
400 {"errorCode":"MISSING_REQUIRED_FIELD","error":"Missing required field: messages"}
```

从 `401` 变成 `400`，说明请求**已经穿过门禁、进到业务处理器**。补上合法的 `messages` 与模型名，就会真实调用上游模型。

**根因**

`lib/physics/account-store.ts:51`：

```ts
const SESSION_COOKIE_PATTERN = /^[A-Za-z0-9._-]{1,128}\.\d{10,16}$/;
```

令牌内容就是 `<userId>.<登录时间戳>`，由**浏览器自己写入**（`setSessionCookie`），服务端只做正则形状匹配。`middleware.ts` 与 `scripts/prune-edgeone-function.mjs` 生成的云函数入口用的是同一套判定。代码注释里已诚实写明「验证不了是不是本人」，但实际风险比注释描述的更重：注释说它「挡得住随手匿名调用」，而实际上连「随手」都挡不住——任何人都能在 10 秒内构造出合法形状。

**影响**

`/api/generate/*`（含 TTS、图像、视频）、`/api/chat`、`/api/agent/*`、`/api/transcription`、`/api/web-search` 全部对公网开放。这些接口烧的是部署者自己的 Makers Models 额度。叠加 P1-1（零限流），一个 `for` 循环就能把额度打空。

**建议修法（按代价从低到高）**

1. **HMAC 签名（推荐，约半天）**：服务端持一个 `SESSION_SECRET`，签发 `userId.exp.hmac(userId + exp, secret)`；门禁验签 + 验过期。账号仍在 localStorage，只是「登录成功」这一步改为向 `/api/session` 换一张签名票。客户端拿不到密钥，无法伪造。
2. **若坚持无服务端状态**：至少把门禁换成「按 IP + 令牌的滑动窗口限流 + 每日总量配额」，把「无限白嫖」降级为「有限白嫖」。但这只是止血，不解决身份问题。
3. 无论选哪条，都要在参赛材料里改口径：现在写的是「会话门禁挡住匿名调用」，实际挡不住，评委会问。

## P1

### P1-1　全站零入站限流

**证据**：全仓检索 `rateLimit`，只命中 `lib/server/classroom-media-generation.ts` 里对 **TTS 上游** 的退避重试——那是出站，不是入站。58 个 API 路由没有一个做请求频率限制。

**影响**：与 P0-1 叠加后，攻击者可以无限并发。即使 P0-1 修好，单个合法账号也能瞬间打满额度。

**建议**：令牌桶，按 `userId` + `IP` 双维度；生成类接口建议「每 10 分钟 N 次 + 每日 M 次」。EdgeOne 有 KV，或用 Upstash Redis（免费额度足够）。

### P1-2　课堂数据落在云函数的临时文件系统

**证据**

- `lib/server/classroom-storage.ts:17`：`CLASSROOMS_DIR = path.join(process.cwd(), 'data', 'classrooms')`
- 线上 `/api/stages` 直接返回 `404 Not found`（持久化层未启用）
- `classroom-media` 路由里 `readStageAccessIncludingDeleted` 只在 `process.env.DATABASE_URL` 存在时才执行，注释明写「local-only mode」

**影响**：EdgeOne 云函数是多实例、实例可回收的。文件写在 `process.cwd()` 下意味着：A 实例生成的课堂，B 实例可能读不到；实例被回收后数据消失。对「老师备好一堂课，明天上课用」这个核心场景是致命的。

**建议**：接 `DATABASE_URL`（仓库里已有 `storage-pg-contract` 工作流和 `owner-bound-document-store` 抽象，接入成本不高），媒体文件走对象存储。若短期不做，至少在 UI 上明确标注「当前为演示模式，课堂不保证长期保存」，并把文档里「课堂可留存」的表述改掉。

### P1-3　学习进度持久化静默失败

**证据**

`lib/physics/local-store.ts:381`：

```ts
export function saveState(...): boolean {
  try { storage.setItem(...); return true; }
  catch { return false; }   // 返回 false 表示没写进去
}
```

`components/physics/state-provider.tsx:160`：

```ts
saveState(state, undefined, scope);   // 返回值被丢弃
```

**影响**：localStorage 写满（5 MB 上限、Safari 无痕模式、用户禁用存储）时，学生闯关进度、诊断结果、实验记录全部丢失，**界面上没有任何提示**。学生会以为「已经保存了」，第二天回来一切归零。

**建议**：检查返回值；失败时 toast 提示 + 降级到内存态；同时在写入前清理过期的 undo 快照（`lib/physics/undo.ts` 的快照没有容量上限）。

### P1-4　路由声明的超时与平台上限冲突（300s vs 120s）

**证据**

- 12 个路由声明 `export const maxDuration = 300`：`chat/pi`、`agent/owner-events`、`agent/sessions/[id]/events`、`stages/[id]/freshness`、`pbl/v2/{open-task,evaluate,simulator,instructor}`、`generate/{video,image,scene-content,scene-outlines-stream}`
- `edgeone.json`：`cloudFunctions.maxDuration = 120`
- `scripts/deploy-edgeone.mjs:596`：超过 120 直接拒绝部署

**影响**：平台按 120 秒切断，而代码按 300 秒设计。SSE 流（`/api/chat/pi`、agent events、freshness）在 120 秒被硬切，客户端表现为「回答说到一半停住」，且没有错误码——用户以为是网络问题。

**建议**：把路由声明统一改成 120，与实际能力对齐；真正需要长时间的任务改异步作业（仓库已有 `classroom-job-store` 这套模式可复用）；SSE 加心跳与断线重连（`Last-Event-ID`）。

### P1-5　软 404：不存在的路由返回 200

**证据（线上实测）**

```
/physics/overview     -> 200
/physics/not-a-view   -> 200
/teacher/not-a-view   -> 200
/classroom/not-a-classroom -> 200
```

**根因**：`app/physics/[view]/page.tsx` 有 `generateStaticParams` 列出 8 个视图，但既没有 `export const dynamicParams = false`，组件里也没有 `notFound()`。`teacher` 与 `classroom` 同样。

**影响**：SEO 上产生大量重复页；用户手改 URL 会看到一个「正常渲染但内容不对」的页面，比 404 更困惑。

**建议**：`dynamicParams = false` + 路由组件内对未知参数 `notFound()`；`classroom` 页对不存在的 id 走 `notFound()`。

## P2

### P2-1　安全响应头不完整

线上实际只返回两个：`X-Frame-Options: SAMEORIGIN` 与 `Content-Security-Policy: frame-ancestors 'self'`（`next.config.ts` 的 `headers()`）。

缺 `X-Content-Type-Options: nosniff`、`Strict-Transport-Security`、`Referrer-Policy`、`Permissions-Policy`，以及真正限制脚本来源的 CSP（`script-src`）。

**为什么值得修**：全站有 11 处 `dangerouslySetInnerHTML`，安全性完全押在 `lib/server/sanitize-scene-content.ts` 这一层白名单上（这份实现质量不错，按标签/属性/CSS 属性逐项允许）。但白名单只要漏一个标签（历史上 `sanitize-html` 就出过 mXSS 类问题），没有 CSP 就没有第二道防线。建议先上 `Content-Security-Policy-Report-Only` 观察一周再转强制。

### P2-2　部分接口请求体无大小限制

`/api/materials` 做得很好（声明长度校验 + 读取时二次校验 + 每 owner 字节配额）。但 `/api/generate-classroom` 接收 `pdfContent: { text, images: string[] }`（base64 图片数组），只校验类型不校验体积，`req.json()` 会把整个 body 读进内存。构造一个几百 MB 的 JSON 就能把函数内存打爆。

**建议**：统一在 `lib/server` 加一个 `readJsonWithLimit(req, maxBytes)`，所有 POST 路由改用它。

### P2-3　账号表「读—改—写」无锁

`lib/physics/accounts.ts:353`：`await repository.save([...accounts, account])`。`list()` 与 `save()` 之间没有互斥。两个标签页同时注册，后者会用自己那份快照覆盖前者，先注册的账号消失。

**建议**：用 `navigator.locks.request('physics-accounts', ...)` 串行化（浏览器原生，无需依赖）；写入前重读并合并。

### P2-4　会话 Cookie 缺 `Secure`

`account-store.ts:233`：

```ts
document.cookie = `${SESSION_COOKIE_NAME}=${value}; path=/; max-age=...; samesite=lax`;
```

没有 `Secure`。HTTPS 站点应补上，避免任何降级场景下明文传输。

需要说明的是 `HttpOnly` **做不到**——这个令牌本来就是客户端读出来再放进请求头的（`session-header.ts` 的 fetch 补丁），加了 `HttpOnly` 整条链路就断了。这是设计取舍，应该在文档里写明，而不是留成隐患。

### P2-5　匿名 owner 配额可绕过

`lib/server/agent-runtime/with-owner.ts` 的 owner 身份来自 Cookie，清掉 Cookie 就是全新 owner。材料上传的 `maxCount` / `maxTotalBytes` 因此可以无限重置。

**建议**：与 IP 做弱绑定，或对上传接口加全局速率限制（与 P1-1 一并解决）。

### P2-6　测试套件长期不绿，真回归会被淹没

实跑 `tests/physics` + `tests/server`：

```
Test Files  11 failed | 62 passed (73)
Tests       24 failed | 939 passed (963)
```

其中 16 个是 `Test timed out in 5000ms`（本机负载导致，非逻辑错误），8 个是真断言失败，包括：

- `model-authorization-coverage-matrix.test.ts`：`chat: not-listed refuses before any upstream call` —— 期望「未授权模型不得触达上游」，实际被调用 1 次
- `url-guard-unconditional-invariant.test.ts`：SSRF 调用点不得被 `NODE_ENV` 包裹
- `classroom-route-no-overwrite.test.ts`：期望 201/409，实际 500

后两组涉及**安全契约**，无论是不是环境问题都必须人工确认。

**建议**：`testTimeout` 提到 20s；网络型用例打 `@slow` 标签拆到单独 project；安全契约测试单独一个 `--project=contract` 并要求 100% 绿。

### P2-7　没有依赖漏洞扫描

`pnpm audit` 在当前镜像源上直接失败：

```
ERR_PNPM_AUDIT_ENDPOINT_NOT_EXISTS
The audit endpoint (at https://registry.npmmirror.com/...) doesn't exist
```

CI（`.github/workflows/ci.yml`）里也没有 audit 步骤。也就是说，目前**没有任何机制**发现依赖漏洞。

**建议**：CI 加 `npm audit --registry=https://registry.npmjs.org --audit-level=high`，或用 `osv-scanner`（不依赖 registry 端点）。

## P3

### P3-1　巨型单文件

| 文件 | 行数 |
| --- | --- |
| `lib/ai/providers.ts` | 2740 |
| `lib/store/settings.ts` | 2567 |
| `components/chat/use-chat-sessions.ts` | 2363 |
| `lib/session/session-store.ts` | 2228 |
| `components/roundtable/index.tsx` | 2197 |
| `app/page.tsx` | 1950 |

单文件两千行以上，意味着：改一处要在两千行里找上下文、code review 实际失效、按需加载粒度粗（一个 hook 文件拖进整条链路）。建议按职责拆分，优先拆 `use-chat-sessions.ts` 与 `app/page.tsx`。

### P3-2　类型逃逸与日志不统一

`as any` 27 处、`console.log` 2 处（其余均走 `lib/logger`）。数量不大，但 `as any` 集中在 provider/媒体适配层，正是最容易因上游协议变更而出错的地方。

### P3-3　首屏体积

实测（Playwright，Chrome，1280×800）：

```
TTFB 1.18s | load 3.64s | 水合完成 3.68s
34 个 JS chunk，合计 801 KB，最大单块 233 KB
```

这个数字比之前观测到的「13 秒 DOM / 23 秒水合」好得多，那次应该是冷启动叠加未缓存。当前状态可以接受，但 801 KB 对首屏仍偏重。建议对工作台、课堂播放器做路由级 `dynamic()`，把首屏压到 400 KB 以内。

### P3-4　公开接口暴露配置画像

`/api/server-providers` 无鉴权返回：

```json
{"providers":{"openai":{"models":["minimax/minimax-m3"]}},"generation":{"parallelSceneConcurrency":4}}
```

`/api/health` 也公开了能力开关。信息价值不高（拿不到密钥），但属最小暴露原则问题，建议对非公开部署收敛。

### P3-5　进程内互斥在多实例下无效

`lib/server/classroom-job-store.ts:60` 用 `Map<string, Promise>` 做 per-job 互斥。这在单进程内是对的，但云函数是多实例的，两个实例同时改同一个 job 文件仍会互相覆盖。文件写入本身用了 `writeJsonFileAtomic`，所以不会写出半个文件，但「读—改—写」的竞态还在。建议改用文件锁或数据库乐观锁（`updatedAt` 版本号）。

## 建议的修复顺序

1. **P0-1 + P1-1 一起做**（签名 + 限流）——这是唯一「现在就在漏钱」的问题，且改动集中在 `account-store.ts` / `middleware.ts` / `prune-edgeone-function.mjs` 三处，契约测试已经在了，改完能立刻验证。
2. **P1-2**（数据持久化）——决定这个产品是「能上课」还是「只能演示」，优先级高于所有 P2。
3. **P1-3 / P1-4 / P1-5**——都是小改动，一天内可以全部收掉，收益直接体现在演示稳定性上。
4. **P2-6 / P2-7**——先把测试和依赖扫描恢复到可信状态，否则后面所有修复都没有回归保护。
5. 其余 P2、P3 按迭代排。

**这次没做的事，以及为什么**（避免被读成「已全部修完」）：

1. **没有给会话令牌加签名**。原报告推荐 HMAC，但账号表在 localStorage、服务端零账号状态，签发端点无法判断调用者是谁——加了签名只是把伪造点从「客户端自写」挪到「调用签发接口」，没有实质提升。要根治必须把账号搬到服务端（需要数据库）。所以选了「限流 + 配额 + 体量上限」，把「无限白嫖」降级为「有限白嫖」，并同步改口径。
2. **没有接数据库**。课堂数据的生命周期问题（P1-2）仍在，只是从「隐性」变成「显性」：界面、部署文档、交付文档三处都写明了。
3. **强制 CSP 的 `script-src` 缺席**。这是平台约束（无中间件 → 无 nonce），不是省事。Report-Only 那份就是用来量差距的。
